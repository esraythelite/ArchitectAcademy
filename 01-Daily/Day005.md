## Before Coding

### What is the responsibility of the Domain layer?

The Domain layer is responsible for representing business concepts, business rules and business behavior.

It contains entities, value objects, aggregates and domain rules. 

### What is the responsibility of the Application layer?

The Application layer is responsible for coordinating application use cases.

It receives requests, calls domain behavior and coordinates external dependencies when needed.

### What is a Use Case?

A use case represents a specific action or goal that a user or another system wants to perform through the application.

### Should the Application layer contain business rules? Why?

Core business rules should not live in the Application layer.

The Application layer should orchestrate use cases, while business rules should be protected by the Domain layer.

This prevents business rules from being duplicated across different use cases.

### Should the Domain layer know about HTTP, controllers or databases? Why?

No.

The Domain layer should not depend on HTTP, controllers or database technologies because these are infrastructure and delivery concerns.

The Domain should focus only on business concepts and business rules.

### What is the difference between application orchestration and domain logic?

### What is the difference between application orchestration and domain logic?

Application orchestration coordinates the steps of a use case.

Domain logic defines and protects business rules and business behavior.

For example, StartOnboardingHandler coordinates the creation of value objects and the Onboarding aggregate, while the Domain decides whether those objects and state transitions are valid.

## Part 2 — API Layer

### What is the responsibility of the API layer?

-API layer is responsible for taking api request and sending response.
*The API layer is responsible for handling transport concerns.

It receives HTTP requests, maps them to application commands, calls the application layer and converts application results into HTTP responses.

### Should the API contain business rules?

No. Core business rules should live in the Domain layer.

### What is the difference between an HTTP request model and an Application command?

-HTTP request is a formated request can be json or xml and needs an endpoint to reach another.On the other hand Application command is an object created and terminated in the application.
*An HTTP request model represents the contract exposed by the API.

An Application command represents the input of a specific application use case.

Keeping them separate prevents the Application layer from depending on HTTP contracts and allows the API contract to evolve independently.

### Why shouldn't the Domain return HTTP status codes?

-Domain organize business rules and in the API layer ve can express the result messages as an http status codes. Domain should not know about http.

*HTTP is a transport concern.

The Domain should describe business outcomes without knowing whether the application is accessed through HTTP, messaging, CLI or another interface.

The API layer is responsible for translating application/domain outcomes into HTTP status codes.

### Which HTTP status code should StartOnboarding return when successful?

-201 code is meaningful since it is an post request and in the end an onboarding object must be created.

*201 Created.

The request creates a new Onboarding resource, so 201 Created is more appropriate than 200 OK.

Ideally, the response can also include the location of the newly created resource.

***
Domain does not know HTTP exists.
Application does not need to know HTTP exists.
API knows both HTTP and Application.
***

### Why do we have StartOnboardingRequest if StartOnboardingCommand already exists?

Because the API request model and the application command represent different boundaries.

The request model represents the external HTTP contract, while the command represents the application use case.

Keeping them separate allows the API and Application layers to change independently.

## Part 3 — Error Handling

### Is an invalid IdentityNumber an expected or unexpected failure?

It is an expected failure. 
Invalid input is a normal business scenario that can occur during application usage.
It should be handled gracefully instead of being treated as an unexpected system failure.

### Should this error return 400, 404, 409 or 500? Why?

It should return 400 Bad Request because the request contains invalid input.

404 is for a resource that cannot be found.
409 is typically used for a conflict with the current state of a resource.
500 represents an unexpected server-side failure.

### Why should the Controller not catch ArgumentException itself?

The Controller should not handle the same exception repeatedly.

If every Controller contains its own try/catch blocks, error handling logic becomes duplicated and inconsistent.

Cross-cutting error handling should be centralized.

### Which layer should translate a Domain/Application error into an HTTP response?

HTTP is a transport concern, so the API layer should translate Domain/Application failures into appropriate HTTP responses.

### Error Handling Result

Invalid domain input is translated by the API layer into an HTTP 400 response using a global exception handler.

The Domain remains unaware of HTTP, while the API is responsible for converting exceptions into ProblemDetails responses.

Current flow:

Domain Exception
→ GlobalExceptionHandler
→ ProblemDetails
→ HTTP Response

## Part 4 — Dependency Injection

### Why shouldn't the Controller create the Handler with `new`?

The Controller should not be responsible for creating its dependencies.

Dependency Injection reduces coupling and allows dependencies to be replaced, configured and tested independently.

The Controller only declares what it needs, while the DI container is responsible for creating the required objects.
