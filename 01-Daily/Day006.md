# Day 006 — Persistence Boundary & Repository

Date: 14 September 2026

## Goal

Persist the Onboarding aggregate without making the Domain depend on EF Core or a database.

## Before Coding

### Should the Domain layer know EF Core exists? Why?

No.

The Domain layer should not depend on EF Core or any database technology.
It should focus only on business concepts, rules and behavior.

### Where should the repository abstraction live?

Application
    ↓ knows
IOnboardingRepository

Infrastructure
    ↓ implements
IOnboardingRepository

The repository abstraction should live in the Application layer because the Application layer defines what persistence capability the use case needs.

Infrastructure provides the implementation of that abstraction.  ***Dependency Inversion Principle

### Where should the repository implementation live?

The repository implementation should live in the Infrastructure layer because it contains database-specific persistence logic such as EF Core.

### Why shouldn't StartOnboardingHandler directly use DbContext?

Because the Application layer should not depend directly on EF Core or database-specific infrastructure.

Injecting DbContext would couple the use case to a specific persistence technology.

The Handler should depend on a repository abstraction instead.

### What is the difference between a Repository and DbContext?

A Repository provides a domain-oriented abstraction for persistence operations.

DbContext is an EF Core infrastructure component responsible for tracking entities, querying data and communicating persistence changes to the database.

The Application layer should depend on repository abstractions rather than directly depending on DbContext.

### Should the repository return Domain entities or database models?

The repository should return Domain entities or aggregates.

Database-specific persistence models should remain inside the Infrastructure layer.

This prevents persistence concerns from leaking into the Application and Domain layers.

### Where should SaveChanges / transaction coordination happen?

Transaction coordination should happen at the application use-case boundary.

Repositories can track or stage persistence changes, while a Unit of Work abstraction can commit them together.

The Infrastructure layer implements the actual transaction and SaveChanges behavior.

## Architect Challenge

StartOnboardingHandler creates a new Onboarding aggregate.

Which design would you choose?

A) Handler directly injects FinPilotDbContext

B) Handler injects IOnboardingRepository

C) Domain aggregate saves itself

D) Controller saves the aggregate

My decision: B

Reason: The Application layer should depend on a repository abstraction rather than a concrete database implementation.

IOnboardingRepository defines the persistence capability required by the use case, while Infrastructure provides the concrete implementation.
