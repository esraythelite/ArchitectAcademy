## Before Coding

### What is an Entity?

-Entity is an object having a one to one relation with a database.
*An Entity is an object that has a unique identity and can change over time while remaining the same conceptual object.

### What is a Value Object?

-Value Object is an object designed for a spesific business and could cover parts of an entity.
*A Value Object is an object without its own identity. It represents a domain concept through its values and is usually immutable.

### What is an Aggregate?

-Aggregate is a type of an object which is allowed to be modified.
*A cluster of related domain objects that are treated as a single consistency boundary.

### What is an Aggregate Root?

-Aggragate Root is a smallest object that all aggregates are inherited its properties from.
*The main Entity that controls access to the Aggregate and protects its business rules.

### Why shouldn't IdentityNumber simply be a string?

-IdentityNumber must be unique for all entities and also it needs to be created new for each entity automatically.
*IdentityNumber should not be a plain string because it has domain-specific rules and meaning. By modeling it as a Value Object, we can prevent invalid values from entering the domain and keep validation logic in one place.

## Architect Challenge

Should Email and PhoneNumber be shared between modules?

My decision:

Yes, for the current FinPilot domain.

Reason:


Email and PhoneNumber currently represent the same domain concepts across multiple modules and use the same validation and normalization rules.

Creating separate implementations for every module would introduce unnecessary duplication.

However, they should only remain shared while their business meaning and rules are the same. If a module requires different rules in the future, it should own its own Value Object.
